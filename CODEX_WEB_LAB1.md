# Задание: первая лабораторная по веб-технологиям

## 1. Цель и контекст

Доработай существующий проект https://github.com/evilthrone/library_db: создай информационный сайт библиотеки вокруг уже работающего приложения к БД. Не создавай отдельный сайт с нуля и не заменяй Java-приложение другим стеком.

Пользователь продолжает проект лабораторных 3-4 по дисциплине «Базы данных». Первая лабораторная по веб-технологиям посвящена информационным страницам, навигации, дополнительным сервисам и поиску по сайту. Предыдущие переписки для выполнения не нужны: контекст и принятые решения приведены здесь.

Этот файл является заданием для будущей реализации, а не отчётом о выполненных изменениях. Само получение этого файла не означает, что сайт уже доработан.

## 2. Проверенный исходный проект

Сведения ниже проверены по исходникам 16 сентября 2026 года, commit `ed8c8eb97f8010cb4d1c1e221492e143f3d7f146`. При начале работы сравни их с текущим checkout. Актуальный код имеет приоритет над устаревшим описанием реализации, но требования задания сохраняются.

### Стек

- Java 21, Gradle Wrapper, Spring Boot 4.0.5.
- Spring MVC, Thymeleaf, Bean Validation.
- JDBC / JdbcTemplate, PostgreSQL и MySQL.
- Обычные CSS и JavaScript, без SPA-фреймворка.
- В build.gradle нет Spring Security и JPA. Не приписывай проекту эти технологии.

Особенности, которые нельзя потерять:

- «Вход как читатель/сотрудник» сейчас является выбором меню, а не авторизацией. Не описывай его как защиту доступа.
- Записи в обе БД в `DualDatabaseLibraryService` выполняются последовательно. Не заявляй атомарность между БД.
- Форма книги загружает справочники из PostgreSQL; добавление книги в MySQL при определённых входных данных также обращается к PostgreSQL за названиями. Не обещай независимость этих сценариев от PostgreSQL и не исправляй архитектуру БД попутно.
- README требует заранее подготовленные БД `library_db` и `library_db_mysql`. В проверенном дереве нет SQL-миграций/дампа для развёртывания схемы. Не выдумывай полную схему и не запускай разрушительную инициализацию.

## 3. Принятые решения и границы первой лабы

Пользователь утвердил десять информационных страниц из раздела 4.

Под «сервисом» понимается отдельная полезная программа, инструмент или виджет: погода, валюта, калькулятор и т.п. Это не Java-класс `@Service`, не микросервис и не просто внешняя ссылка.

Рабочее решение для количества: реализовать 10 дополнительных инструментов, не включая в их число обязательный поиск по сайту и существующее приложение БД. Конкретный набор ниже предложен как план реализации; пользователь отдельно каждый инструмент не утверждал. Используй этот набор по умолчанию, если не поступили новые указания.

Статические страницы означают заранее написанное информационное содержимое без загрузки основного текста из БД. Разрешено отдавать их Spring MVC + Thymeleaf и использовать общие фрагменты. Это рабочая трактовка задания, а не подтверждённое преподавателем требование к технологии.

Не входят в эту работу:

- XML-доступ к данным: лабораторная 2.
- Ввод, редактирование и показ новостей из БД: лабораторная 4.
- Объединение новостей с внешней лентой: лабораторная 4; вероятно, RSS, но исходная запись преподавателя неоднозначна.
- Новая система авторизации, переписывание JDBC на JPA, миграция на React, микросервисы, полный рефакторинг БД.

Не добавляй неработающие пункты меню «XML» или «Новости». Будущие работы обозначь в README. Если позже пользователь попросит статическую страницу новостей, она может быть дополнительной, сверх утверждённых десяти.

## 5. Общий макет и интеграция с текущими страницами

- Создай общие Thymeleaf-фрагменты шапки, меню, поиска и подвала.
- Примени их к десяти страницам, инструментам, результатам поиска и существующим HTML-экранам БД, включая страницу ошибки там, где это технически возможно.
- Шапка: простой узнаваемый логотип, название и краткое указание назначения сайта. Логотип ведёт на `/`.
- Подвал: контактные данные, сведения о разработчике, отметка учебного проекта.
- Горизонтальное меню на широком экране, удобная адаптация на узком. Выпадающие разделы должны открываться также клавиатурой и нажатием, а не только наведением.
- Возможная структура: «Главная», «О библиотеке», «Читателю», «Полезные ресурсы», «Приложение БД», «Сервисы», «Контакты». Вложенные пункты покрывают все информационные страницы.
- Показывай текущий раздел. Не добавляй ссылки с `href="#"`, которые выглядят работающими, но ничего не открывают.
- Сохрани стиль и доступность существующих форм; не ломай используемые JS идентификаторы, поля, data-атрибуты и обработчики.

Новая главная занимает `/`. Прежний экран выбора читателя/сотрудника перенеси на `GET /app`, например в `app-menu.html`. Меню «Приложение БД» ведёт туда. Существующие `/reader` и `/staff` остаются. Исправь внутренние ссылки «Назад», которые должны возвращать в меню приложения, а не на новую информационную главную.

Не регистрируй два обработчика `GET /`: измени существующий mapping и явно раздели ответственность контроллеров.

## 6. Поиск по всему сайту

На каждой HTML-странице должна быть одна и та же доступная форма поиска. Результаты: `GET /site-search?q=...`.

Это поиск страниц сайта, а не существующий поиск книг в БД.

- Индексируй заголовки, основной текст и дополнительные ключевые слова десяти страниц; включи страницы инструментов и публичные описания приложения.
- Не индексируй персональные данные читателей, результаты отчётов и содержимое закрытых/служебных данных.
- Реализуй локальный поиск без зависимости от индекса Google/Яндекса и без Elasticsearch.
- Минимум: нечувствительность к регистру, обработка пробелов, разумная обработка `е/ё`, поиск по словам; заголовочные совпадения выше совпадений в тексте.
- Результат содержит заголовок, краткий фрагмент или описание и рабочую ссылку.
- Предусмотри пустой запрос и отсутствие результатов. Не выдавай все страницы случайным образом как «найденные».
- Экранируй ввод, не вставляй сырой запрос через innerHTML или th:utext.
- Не создавай индекс, в котором текст никак не связан с реальным содержимым страниц. Предпочти формирование индекса из подготовленных страниц либо единый источник содержимого. Для явного небольшого реестра обеспечь проверку согласованности.

Контрольные запросы: «читательский билет» находит `/membership`, «возврат» находит `/rules`, «время работы» находит `/contacts`. Убедись, что эти слова или их согласованные ключевые слова действительно присутствуют в индексе.

## 7. Десять дополнительных сервисов

Создай каталог `/services` с десятью карточками. Для каждого сервиса используй отдельный маршрут `/services/<slug>` и общий макет. Простая ссылка на внешний сайт не засчитывается как реализация.

| № | Сервис / slug | Минимальная работающая функция |
| --- | --- | --- |
| 1 | Погода / `weather` | Погода для настроенного города: температура, условия, время актуальности и источник |
| 2 | Курсы валют / `exchange-rates` | Курсы выбранных валют к рублю, дата данных и источник |
| 3 | Карта / `map` | Интерактивная карта выбранного адреса/точки, масштабирование; демонстрационная точка явно помечена |
| 4 | Калькулятор печати / `printing` | Число страниц, тип печати, итоговая стоимость; учебные тарифы подписаны |
| 5 | Калькулятор возврата / `return-date` | Дата выдачи + срок в днях = дата возврата; правило расчёта подписано |
| 6 | Планировщик чтения / `reading-plan` | Объём книги, уже прочитано, число дней; результат в страницах в день |
| 7 | Таймер чтения / `reading-timer` | Настройка длительности, старт, пауза, сброс и завершение |
| 8 | Проверка ISBN / `isbn` | Проверка ISBN-10 и ISBN-13 с контрольной цифрой, допускаются пробелы и дефисы |
| 9 | Счётчик текста / `text-counter` | Количество символов с пробелами/без пробелов и слов в введённом тексте |
| 10 | Конвертер времени / `time-converter` | Перевод между минутами, часами и днями, например для планирования чтения |

Требования к реализации:

- Инструменты должны реально работать. Не показывай фиктивную погоду или курсы как актуальные.
- Для внешних данных подбери доступные источники по актуальной документации: HTTPS, условия использования, необходимые подписи/атрибуция. Предпочти бесплатные источники без регистрации и секретных ключей, если они подходят.
- При необходимости используй небольшой серверный адаптер с фиксированным разрешённым источником. Не создавай открытый proxy по произвольному URL пользователя.
- Для запросов: таймаут, обработка недоступности, загрузочное состояние. Для серверных запросов добавь простое разумное кеширование и обозначай время данных.
- Ошибка внешнего провайдера не должна ломать страницу или весь сайт. Покажи честное сообщение; не маскируй неисправность случайными значениями.
- Проверяй числовой ввод, отрицательные значения и деление на ноль. Объясняй результат пользователю.
- Не записывай результаты калькуляторов в библиотечную БД. Для локальных инструментов достаточно JavaScript.
- Не дроби один инструмент на несколько карточек для искусственного набора количества.
- Погода и карта используют единые настройки города/координат. Без реального адреса не изображай демонстрационную точку как адрес настоящей библиотеки.

## 9. Валидация, публикация и индексация

Требования преподавателя: проверить HTML валидатором W3C, предоставить публичный адрес сайта, зарегистрировать сайт в поисковой системе, отправить адрес преподавателю. Разделяй подготовку в коде и внешние действия.

В коде:

- Корректные label, alt, id, вложенность элементов, доступный фокус.
- Проверка итогового HTML, который отдаёт сервер, а не исходных Thymeleaf-шаблонов: https://validator.w3.org/ или https://validator.w3.org/nu/.
- Проверить все информационные страницы и остальные типы экранов; исправить ошибки, описать оставшиеся предупреждения.
- Подготовить `robots.txt` и `sitemap.xml` с каноническим публичным адресом из конфигурации. Sitemap содержит только реально существующие публичные страницы, без параметризованных поисковых результатов, форм записи и персональных данных.
- Не подставлять выдуманный production-домен и не выдавать localhost за публичный адрес.

В README:

- Описать запуск Java-приложения и необходимые подключения к обеим БД.
- Описать публикацию на инфраструктуре, которая поддерживает Java 21/Spring Boot и подключение к БД. Хостинг только статических файлов не запускает это приложение.
- Описать подтверждение владения сайтом в выбранной поисковой системе, отправку sitemap и запрос индексации.
- Предупредить по существу: регистрация/запрос индексации не гарантируют фактического появления в выдаче к конкретной дате.

Публикацию и действия в аккаунте поисковика выполняй при наличии соответствующих доступов и разрешения пользователя. Их отсутствие не блокирует реализацию и локальную проверку. Не отправляй сообщения преподавателю без отдельного поручения. Чётко укажи, какие внешние шаги остались.

До публичного размещения учти, что существующие меню не защищены авторизацией: нельзя публиковать настоящие персональные данные и незащищённую рабочую БД. Для учебной демонстрации используй отдельные демонстрационные данные. Не начинай самовольно большой проект авторизации.

## 11. Проверка результата

Команды из корня проекта:

```bash
# Linux/macOS
./gradlew test
./gradlew bootJar
./gradlew bootRun
```

```powershell
# Windows
.\gradlew.bat test
.\gradlew.bat bootJar
.\gradlew.bat bootRun
```

Используй Java 21. Если gradlew не исполняемый, можно вызвать `bash ./gradlew ...`. Не утверждай, что приложение проверено в работе, если удалось только собрать JAR. Если нет БД, схемы или сетевого доступа к зависимостям, укажи точную границу проверки. Не подменяй отсутствующие БД фиктивными успешными результатами.

Добавляй только полезные проверки: ключевые случаи поиска, ISBN, числовые границы калькуляторов, доступность маршрутов без обращения информационных страниц к данным БД. Для внешних источников проверь успешный ответ и недоступность без зависимости автоматических тестов от живого API. Не пиши отдельный тест на каждый абзац текста.

### Критерии приёмки

- [ ] Сохранён исходный стек и существующие функции приложения БД.
- [ ] Все десять утверждённых информационных страниц имеют отдельные рабочие URL.
- [ ] `/` является новой главной, `/app` содержит прежний выбор режима.
- [ ] Общая шапка, логотип, меню, поиск и подвал есть на HTML-экранах сайта и приложения.
- [ ] С каждой страницы понятно назначение сайта; контакты и разработчик доступны в подвале.
- [ ] Поиск действительно находит страницы по заголовкам/содержимому, а не только книги.
- [ ] Работают десять отдельных инструментов сверх поиска и БД.
- [ ] На `/resources` размещены 5-10 релевантных внешних ссылок.
- [ ] Нет сломанных внутренних ссылок, конфликтов mappings и потери параметров существующих форм.
- [ ] Меню, поиск и инструменты доступны клавиатурой, интерфейс пригоден на узком экране.
- [ ] Отказы внешних источников обработаны; актуальные данные не выдуманы.
- [ ] Итоговый HTML проверен W3C, результаты честно зафиксированы.
- [ ] Сборка и доступные проверки выполнены, ограничения окружения указаны.
- [ ] README содержит необходимые настройки, инструкции запуска и публикации.
- [ ] Публичный URL и индексация указаны только если реально выполнены; иначе перечислены оставшиеся шаги.

## 12. Как общаться с владельцем

Объясняй изменения по-русски, кратко и понятно. Владелец знает Java и изучает backend; ему нужно понимать устройство проекта и уметь защитить работу. При описании решений связывай код с требованием лабораторной. Не утверждай, что преподаватель одобрил спорные трактовки. Самостоятельно решай обычные детали реализации, а отсутствие реальных контактов или доступа к хостингу фиксируй отдельно, не останавливая остальную работу.
